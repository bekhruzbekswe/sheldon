# L6 — Synthesis

> **Status: shipped 2026-05-05** (change `add-synthesis`). Reality differed from plan in one important way — see the "What actually shipped" note at the bottom.

## Goal

When the synthesis phase fires (per L5), produce a written research report. The fact store may have hundreds of claims across many sources — too much for one LLM call. We cluster facts into themes, write one section per cluster, then stitch with intro and conclusion. Output: `report.md` with inline `[N]` citations linking to source URLs.

This layer is where most of the perceived quality of Sheldon comes from. The earlier layers gather; this one delivers.

## Capabilities introduced

- `cluster-facts` — embedding-based clustering of all stored facts into 5–10 themes (k-means or hierarchical agglomerative)
- `section-writer` — LLM prompt that takes one cluster's facts and writes a 200–500 word section with inline citations
- `report-stitcher` — programmatic concatenation of intro + sections + conclusion + bibliography; renders to markdown
- `intro-writer` and `outro-writer` — small LLM prompts that get only section *headings* (not full content) plus the original task; write framing text

## Dependencies

- L0, L1, L3 (fact-store, embedder), L5 (phase trigger)

## Key data structures / decisions

**Clustering approach:**
- Pull all facts from `fact-store` along with their embeddings.
- Run k-means with `k` chosen via simple silhouette analysis in range 5–10.
- Each cluster gets a label: pick the most common `topic_tag` among its members, or have the LLM name the cluster from the top-5 closest-to-centroid facts.
- Drop tiny clusters (<5 facts) — they're outliers, fold into "Notes" appendix or discard.

**Section-writer prompt (draft → revised after smoke test):**
- Mode: `llm.fast()` (originally planned as `llm.deep`; see "What actually shipped" below for why we changed).
- Input: cluster name, the original task (for framing), facts in the cluster (numbered, with source URLs; capped at 12 closest-to-centroid in the implementation), word target.
- Instructions: "Write a 200–500 word section titled <name> answering <task>. Cite every claim using `[N]` where N matches the input fact number. Use the LLM's own connective tissue — do not just list claims. If two claims contradict, note the disagreement and cite both."

**Report shape:**
```
# <user's task>

Generated by Sheldon on <date>. Researched for <duration>.
<one-paragraph intro from intro-writer>

## <Cluster 1 title>
<section text with [1][2] citations>

## <Cluster 2 title>
...

## Conclusion
<from outro-writer>

## Sources
[1] <title> — <url>
[2] <title> — <url>
...
```

**Citation numbering:** stable across the whole report. The stitcher re-numbers [N] in each section to global [N], maintaining the mapping. This means each section is written independently with its own local numbering, then post-processed.

**Section size budget:** 8 sections × 500 words = 4k words. Each section's prompt fits 30–60 facts × 50 tokens = 3k tokens of facts + instructions ≈ 4k input tokens. Well within 32k context.

**Output location:** `.sheldon/reports/<run-id>.md` plus a symlink at `.sheldon/reports/latest.md`.

## Out of scope

- HTML / PDF rendering — markdown only
- Streaming the report to the user as it's written — the user is at the gym; we deliver finished work
- Cross-section consistency passes — the stitcher just concatenates. If sections contradict, that's surfaced via the LLM's own contradictions in the data, which is honest. A future "polish" layer could do a final pass.
- Pushing the report somewhere (Telegram, email) — separate concern, possibly its own future layer

## Open questions

- Is k-means good enough? Hierarchical clustering might give cleaner topic separation. Try both on first run; pick whichever produces better human-readable groupings.
- Should the section-writer get the *user's original task* in its prompt, or just the cluster? Tentative: yes, brief mention, so sections stay on-topic.
- How do we handle a thinly-researched cluster (only 3 facts)? Either fold into a related cluster, or write a short "open questions" note. Decide at runtime based on cluster sizes.

---

## What actually shipped

The plan said section writers use `llm.deep` (thinking on) because synthesis is the rare quality-critical place where we're willing to spend tokens. The smoke test against 163 facts revealed that doesn't work on Qwen3.5-9B at this prompt shape:

- With ~12 facts of input + section-writer system prompt, Qwen3.5 in thinking mode consumes its **entire output budget** on `reasoning_content` and returns 0 tokens of actual content.
- Bumping `max_tokens` from 1500 → 5000 didn't help — the model just thought longer. At 5000 tokens of generation, generation time exceeded Cloudflare's 100s edge timeout and the connection 524'd. So we hit two failure modes back-to-back: budget-trap at low max_tokens, then 524 at high max_tokens.

**What we shipped instead**: `llm.fast` (no thinking) for sections, intro, and outro. Each section completes in ~17 seconds, produces 296–342 words with 10–12 citations, and fits comfortably under Cloudflare's edge timeout. The smoke test produced a clean 7-section, 17.9 KB report.

**Quality check after first real run**: prose is competent, well-cited, occasionally a touch flat. Acceptable for v1.

**If quality turns out to be a felt problem**, four upgrade paths exist (also recorded in `openspec/specs/section-writer/spec.md` under "Future quality enhancements"):

1. **Streaming responses.** Add SSE streaming to `LlmClient.dispatch`; bytes flowing keep Cloudflare alive past 100s. Re-enables `llm.deep` with much higher `max_tokens` (8000+). 1–2 day change.
2. **Two-pass synthesis.** Keep `llm.fast` for per-section drafting, then add an `llm.deep` polish pass over the stitched draft. One or two deep calls over the full report instead of per-section — short prompts, no budget trap.
3. **Larger / better model.** Qwen3.5-12B-Q5 or a Mistral derivative may behave better in deep mode at this prompt shape. Tradeoff: more RAM.
4. **Tighter clusters.** Switch L3 to `mxbai-embed-large` (1024-dim) for tighter clusters → smaller per-section prompts → deep mode has breathing room.

The first option is the cleanest if we ever go back to chasing deep-mode quality.
